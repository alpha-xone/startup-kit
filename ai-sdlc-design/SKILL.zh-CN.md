# AI 原生 SDLC · 第 2 阶段：Design（设计）

## 边界

只做一件事：**把已接受的 `intent.md` 变成一份已提交的 `spec.md`，边写边应用政策，并标出关注点。**

Design 不做实现规划（那是 `ai-sdlc-build`），也不重新讨论这件事该不该做。如果意图本身有问题，退回 `ai-sdlc-plan`，不要绕着它做设计。

## 这个 skill 固化的转变

| | 传统 | AI 原生 |
|---|---|---|
| 结构 | 需求与设计是两个阶段，两个团队 | 两者在一次提示会话里合并完成 |
| 政策 | 几周后的评审里才被发现 | 写 spec 的同时就被读取并应用 |
| 产出 | 分析师的需求文档，再被设计师重新解析 | 一份受组织 skill 约束的规格，附带已标出的关注点 |
| 产品负责人 | 委托两个阶段 | 审阅并解决关注点，不写 spec |

把政策当作约束而非检查点，是这个阶段的核心。在 spec 阶段提出的问题只需改一段文字；同一个问题在评审阶段才提出，代价是一轮返工。

## 前置条件

- 已接受的 `intent.md`（第 1 阶段）。不要从口头需求开始——那道关卡正是这个阶段便宜的原因。
- 品牌、安全、合规、体验政策**已经写成 skill**。如果某条政策只存在于 wiki 页面，先把它编码成 skill；否则 agent 无法把它当作约束应用。
- 一位有会话权限的产品负责人。不需要工程能力。

## 怎么执行

1. **打开已加载组织政策 skill 的会话**，附上已接受的 `intent.md`。
2. **跑这一遍。** 指向 `intent.md`，点明约束，要求标出关注点。提示词见 `references/spec-prompt.md`。
   - 前几次手动跑。
   - 形态稳定后，把"接受 `intent.md`"作为触发器。在 DSH 里这是一个提示或一个可挂载的 webhook，而不是自动的合并钩子——见 `references/harness-map.md`。
3. **拿 spec 对照想法审阅。** 它解决了提出的问题吗？`intent.md` 里的待决问题是被回答了，还是被明确顺延了？
4. **先处理标出的关注点。** 这些正是分析师会升级上报的点。产品负责人逐个与**具名政策负责人**解决，必须在工程团队看到 spec 之前。
5. **把 `spec.md` 与 `intent.md` 一起提交。** 这对文件记录了要了什么、决定了什么。
6. **做推进判断。** 接受 spec 就是第 3 阶段（Build）计划模式的起点。组织判定为高风险的，咨询技术负责人——这个判断永远由人来做。

## 关卡

| | |
|---|---|
| **人类负责人** | 产品负责人；每个关注点对应具名政策负责人 |
| **决策** | 接受 spec 进入 Build，或退回 |
| **证据** | 已提交的 spec、**产出它的提示词**、以及当时生效的 skill 版本——全部在版本控制里 |
| **"接受"触发什么** | 第 3 阶段（Build）——计划模式 |

把提示词和 spec 一起留存是刻意的。否则后来的读者无法判断这份 spec 写的时候，哪些约束在生效。

## 政策互相冲突时

这个阶段最有价值的产出是**标出的冲突**，不是悄悄选了一边。指示 agent 把它摊开，而不是按偏好解决：

> 当两条政策无法同时成立时，不要选一边。两条都点名，指明 spec 中受影响的部分，标为关注点交给产品负责人。

这个标记就是路由到政策负责人的东西。一个未被标出的自行解决，就是几个月后在最糟的时点被发现的治理缺陷。

## 不要做

- 不要从尚未被接受的意图开始。那道关卡是这个阶段的全部价值。
- 不要让 spec 悄悄化解政策冲突。
- 不要让设计阶段滑向实现规划——文件路径、顺序、测试属于 `plan.md`。
- 不要丢弃提示词。它属于审计记录的一部分。

## 怎么衡量

**领先指标** —— 同一次变更中 `intent.md` 提交到 `spec.md` 提交之间的耗时，与旧的"需求+设计"周期对比。

**滞后指标** —— 开工之后的规格返工：统计同一变更中日期晚于首次 `plan.md` 提交的 `spec.md` 提交次数。每一次都代表一个做晚了的设计决策。
