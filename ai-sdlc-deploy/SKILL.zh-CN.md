# AI 原生 SDLC · 第 5 阶段：Deploy（部署）

## 边界

只做一件事：**评审双向进行，治理在 agent 行动时被执行，agent 做生产闸门之前的一切、过不去闸门。**

Deploy 不写代码（`ai-sdlc-build`），不产出验证证据（`ai-sdlc-test`）。它决定什么可以到生产，并证明它是被允许的。

## 这个 skill 固化的转变

| | 传统 | AI 原生 |
|---|---|---|
| 评审 | 按人的产出能力规划；质量随评审者负载波动 | 每个 PR 走同一套 pass，发现按严重度排序 |
| 人的注意力 | 读整个 diff | 判断意图与风险：它做到方案想做的事了吗，风险可接受吗 |
| 治理 | 评审周期，执行得不一致 | 在 agent 行动时执行；审批闸门是确定性的 |
| agent 的触达 | 取决于被交代了什么 | 生产闸门之前的一切，而闸门之后结构上什么也做不了 |

## 玩法：AI 参与 PR 评审回路

AI 既给评审也收评审：它按组织政策评审进来的 PR，也处理自己 PR 上的评审意见。

1. **选定实现方式。** 托管代码评审服务，或在 CI 里跑评审的动作。DSH 没有托管评审服务——在会话里用 `review` 与 `security-review` 两个 skill，或在仓库上挂 CI 动作。
2. **把评审策略写成仓库根目录的 `REVIEW.md`**，按组织在意的 pass 划分：bug 与逻辑错误；安全与漏洞；对照 `spec.md`、`plan.md` 与设计原则的合规性。它同时界定什么算 `Important`、什么算 nit、以及什么直接不看。模板见 `references/review-md.md`。
3. **设定人工阈值。** 发现本身不批准也不阻断 PR。分支保护仍然要求代码所有者批准。若想用发现给合并设闸，就读评审发布的机器可读严重度计数。
4. **闭合修复回路。** 评审者或作者在评论里 @ agent，它就处理该评论并推修复；PR 线程同时记录请求与改动。更好的做法：扫掉未解决的评论与失败的检查，直到 PR 变绿、只等代码所有者批准。
5. **把发现反馈进 `AGENTS.md`。** **同一个错误被评审第二次标出时，纠正就作为那次评审的一部分写进 `AGENTS.md`**——而因为评审会读 `AGENTS.md`，从下一个 PR 起这个错就会被拦住。评审还应当标出某次改动让 `AGENTS.md` **过期**了。
6. **每月调优。** 给发现评分让评审者进步，在 `REVIEW.md` 里给 nit 数量设上限。排除生成路径与 CI 已经强制的东西。

## 玩法：真正被执行的审批闸门

这是最常被做成惯例、却被宣称为管控的一环。不要这么做。

1. **列出必须存活的人工审批闸门**——变更管理签字、发布授权、受保护路径的编辑——与工程负责人、变更管理、合规一起过。
2. **把每个闸门表达成确定性的东西。** 只以政策文档形式存在的闸门不是闸门。可用的执行层，按强度排序：
   - **沙箱 / 权限预设**（最强，DSH 原生）：完全不许写的会话用 `read-only`；常规工作用 `workspace-write`；只有一次性工作区才用 `danger-full-access`。
   - **钩子**（Claude Code 风格 `PreToolUse`）：能在工具运行前拦截或转人工审批。桥接包在 DSH 里存在但**未挂载**——见 `references/harness-map.md`。
   - **分支保护**（仓库侧）：让 agent 写的任何东西都变成 PR，没有直推主干的路径。与平台无关；先做这个。
3. **拦截必须能自我解释。** 闸门停下动作时，原因与审批路径必须出现在 agent 的输出里。静默拒绝教不会任何人，只会被绕过。
4. **记录"批准"指什么**——一张已批准的变更单，或发布负责人的签字，点名。

## 玩法：按环境分级自主权

| 环境 | agent 可以做 |
|---|---|
| 开发 | 自由部署 |
| 预发 | 居中——准备并部署，破坏性操作上设闸 |
| 生产 | **只准备发布。** 由发布负责人授权，闸门强制这一点 |

指导原则说一次、永不违反：**agent 可以做生产闸门之前的一切，过不去闸门。**

推论：
- agent 写的一切以 PR 形式到达，走分支保护，没有直推主干的路径。
- 每次非交互运行以 agent 自己的身份行动，日志因此能把它做的与触发它的工程师做的分开。
- 按环境的权限分级决定 agent 在闸门之前能做多少。

## 玩法：CI/CD 与回滚

1. **从只读的判断类步骤开始**——研判构建失败、归纳不稳定测试、起草变更日志。这些不需要写权限，收益立刻兑现。
2. **把写步骤加到既有闸门后面**——修 lint、更新生成文档、处理评审意见。以 PR 形式到达。
3. **把执行放进沙箱。** agent 作业不持有常驻生产凭据。
4. **把部署暴露成受限工具**，而不是一个带凭据的 shell 脚本，这样 agent 的部署能力是白名单而非通用能力。
5. **在需要之前排练回滚。** 回滚应当是流水线里排练最多的路径：一条 agent 能跑的命令，在预发定期演练。`ai-sdlc-maintain` 在控制带被突破时会调用它，所以必须事先验证过。

## 安全姿态:哪一层在强制什么

不要把软层说成硬管控。在 DSH 里，可执行的管控面**比源 playbook 假设的更粗**：

| 关注点 | DSH 的执行情况 |
|---|---|
| 文件写入 | 真实。三种模式：`read-only` / `workspace-write` / `danger-full-access`，按会话记录在会话日志里，重启后仍有效。 |
| 网络出口 | **沙箱不覆盖。** DSH 自己的文档写明：文件效果模式"管的是文件效果；网络与进程策略不在它的词汇表里"。playbook 里那种域名白名单在这一层不存在。 |
| 密钥文件（`~/.ssh`、`.env`、凭据） | **本 profile 没有暴露按路径的拒绝列表。** 不要声称有。把密钥挡在工作区之外，或用一个工作区不包含它们的会话。 |
| 工具白/黑名单 | 没有作为受管策略列表暴露。权限预设就是那个旋钮。 |
| 区分 agent 做的与工程师做的 | 靠身份与 PR 路径（分支保护）达成，不是靠某个受管设置功能。 |

playbook 里那段受管设置（按路径拒绝、网络域名白名单、凭据剥离、`allowManagedHooksOnly`、MCP 白名单）在 DSH **没有对应物**。如果审计方问起，就照实说，并指向确实存在的层：分支保护、只能走 PR 到主干、按环境的权限分级、日志里的 agent 身份。

## 不要做

- 不要把政策文档称作被执行的闸门。点名是哪一层在拦。
- 不要让写了代码的 agent 批准它。职责分离就是重点。
- 不要给 agent 常驻生产凭据。
- 不要在闸门还不存在时先做自动化。闸门先行；自动化只会加速已经在那儿的东西。

## 怎么衡量

**领先指标** —— 首次评审耗时（应降到分钟级）；无需人碰分支就被解决的评审意见占比；无需呼叫人工就被研判的流水线失败占比；在每个审批闸门上的等待时长。

**滞后指标** —— 合并前拦下的缺陷与漏洞，对比逃到生产的那些；DORA 指标（部署频率、交付周期、变更失败率、恢复时长）。
