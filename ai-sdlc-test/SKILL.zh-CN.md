# AI 原生 SDLC · 第 4 阶段：Test（测试）

## 边界

只做一件事：**每个会话在被人看到之前先自查，而给 agent 定方向的配置像它所写的代码一样被回归测试。**

Test 不决定改动该不该上线——那是 `ai-sdlc-deploy`。它产出的证据让那个决定变便宜。

## 这个 skill 固化的转变

| | 传统 | AI 原生 |
|---|---|---|
| 信号何时到 | CI 几分钟后、测试员几天后、生产几周后 | 会话在人看之前先自查 |
| 谁是瓶颈 | 必须检查 agent 全部产出的人 | 如果回路提前搭好，就没有人 |
| Evals | 阶段边界上的 QA 闸门 | 每当 agent 配置变更就跑的活套件 |

有了 agent，这件事更要紧的原因：人写代码时，信号晚到只是等一会儿。agent 写代码时，信号晚到意味着一个人必须检查 agent 产出的一切——而那个人就成了瓶颈。

## 两件不是一回事的东西

| | 反馈回路 | 验证子 agent |
|---|---|---|
| 运行时机 | 贯穿任务全程，工作需要多少次就跑多少次 | 一次，在会话自认为做完之后 |
| 上下文 | 同一会话，同一套假设 | 一个**全新**的上下文窗口 |
| 目的 | 让会话修掉自己的错 | 得到一个不被产出代码时的假设染色的判断 |
| DSH 机制 | 普通测试/构建/运行命令，加上工作区的测试类 skill | `subagent_fork`——它继承方案与改动，只交回判断 |

两者都用。回路让工作干净地到达；验证者防止一个自信的会话给自己打分。

## 前置条件

无，但回路的价值上限就是仓库能跑什么。依赖回路之前：测试套件与构建各自能用一条命令在本地跑起来。

## 怎么执行

1. **把检查收敛成每个关注点一条命令** —— `make test`、`npm test`、`pytest` —— 失败时都以非零码退出。如果今天检查工作需要一串命令加一些环境知识，那正是要先修的东西。
2. **把每条命令写进 `AGENTS.md`，并给一个健康输出的样例。** agent 必须能区分"通过了"和"只是吐了文字"。
3. **给出可量化的目标**，让 agent 不用问就能自查："`test_status.py` 全部通过"、"该端点返回 200 且带新字段"、"截图与附上的原型一致"。
4. **修 bug 时先写失败的测试。** 让 agent 把 bug **复现为一个测试**，跑它，确认它**因你预期的原因**失败。提交这个测试。然后才要求修复，且不许改测试。
5. **UI 工作要用视觉收口。** 给 agent 跑起应用并截图的能力，给它原型，让它迭代：实现、截图、比对、调整。两三轮是正常的。
6. **把验证并入"完成"的定义。** 这条指令住在 `AGENTS.md` 里。报告任务完成之前跑完检查，并把输出贴出来。
7. **保护回路不被 agent 削弱。** 修代码的 agent 绝不能改动检查这段代码的东西。修复任务期间禁止编辑测试文件，或者在评审里拒绝任何"只改测试"的修复。

第 2、3、6 步的模板见 `references/feedback-loop.md`。

## 为什么"先写失败的测试"是承重的

修复**之后**才写的测试什么都证明不了：它的形状由实现决定，无论 bug 是真是假它都会通过。一个测试如果：

- 在修复之前就存在，
- 因所述原因失败过，
- 而且 agent 不被允许改写它，

那它就是 bug 已消失的证据。论证到此结束，这也是第 7 步存在的原因。

## 持续 evals

Evals 是 AI 原生的阶段闸门 QA 等价物——一套在**agent 配置**变更时就会跑的套件，而不只是在代码变更时。

1. 从近期工作里收集 **20–50 个真实任务**，各带预期或被接受的结果。
2. 每个写成一个 eval：提示词，加上界定"可接受"的检查（测试通过、lint 干净、行为不变、政策被遵守）。
3. 按计划非交互地跑，并在 `AGENTS.md`、`CLAUDE.md`、skill 或钩子任何变更时跑。那套配置在给 agent 定方向，它值得和代码同等的回归测试。
4. **用结果给配置变更设闸。** 一个让通过率掉下来的 skill 变更，合并前必须被评审。
5. 每一起生产事故都变成一个 eval，由拥有该事故的团队撰写，并长期留在套件里。

把套件当作活的：模型变强之后，曾经有区分度的用例会失去区分度，必须从持续监控里补新的。

## DSH 现实核对

DSH 没有内置 eval 运行器，也没有供 CI 用的 `claude -p` 非交互模式。要跑 evals，得自己写脚本驱动模型 API，或用既有 CI 承载你定义的检查。什么能对应、什么不能，见 `references/harness-map.md`——不要承诺平台并不提供的 eval 框架。

## 不要做

- 不要把修复之后才写的测试当作证据。
- 不要让 agent 编辑正在评判它的那个测试。
- 不要在没有贴出真实输出的情况下报告任务完成。证据必须来自工具链，而不是 agent 对工具链的总结。
- 不要让 agent 靠跳过或删除失败的测试来变绿。

## 怎么衡量

**领先指标** —— agent 所写改动的一遍 CI 通过率；对 evals 而言是通过率随时间的走势，以及一起生产事故变成常驻 eval 所需的时长。

**滞后指标** —— 每个 PR 的评审耗时（测试接住评审者原本要接的东西之后应当下降）、变更失败率，以及 CI 里拦下的回归与生产里发现的回归之比。
