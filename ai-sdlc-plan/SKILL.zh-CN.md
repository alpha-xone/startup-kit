# AI 原生 SDLC · 第 1 阶段：Plan（规划）

## 边界

只做一件事：**产出一份已提交的 `intent.md`，并让产品负责人接受或关闭它。**

Plan 不决定怎么实现（那是 `ai-sdlc-design` 和 `ai-sdlc-build`），也不做估算。如果你开始写文件路径、技术设计或故事点，你已经越界了。

## 这个 skill 固化的转变

| | 传统 | AI 原生 |
|---|---|---|
| 流转 | 待办条目 → 用户故事 → 故事点 → 细化会议 | `intent.md`，用提出者自己的话写，提交到共享位置 |
| 归属 | 每次交接都转移，语义逐层流失 | 提出者始终是作者，一份制品承载完整意图 |
| 触发 | 有人决定去写下来 | 一个人、一张工单或一条告警，走同样五步 |

制品才是重点。一份已提交的 `intent.md` 既能让产品负责人读懂，也能让下一阶段直接执行，而这次提交本身就是审计记录。

## 前置条件

无。Plan 是唯一没有上游依赖的阶段——从这里开始。

需要一次性搭好的基础设施：
- 一个纳入版本控制的意图存放处。单一产品放在产品仓的 `intent/` 即可；只有意图横跨多个仓时，独立意图仓才值得。
- 一份书面 `intent.md` 模板，由负责人确认。
- 明确谁能写入意图存放处——贡献者会来自组织各个角落。

在 DSH 里，非工程人员完全不需要碰 git：他在会话里描述问题，由 agent 代为提交 markdown。见 `references/harness-map.md`。

## 怎么执行

1. **提出者用自己的话描述问题。** 今天做不到什么、谁受影响、什么算更好、什么不在范围内。先不用正式语言，也不用填模板字段。
2. **追问到想法具体为止。** 问一个分析师会问的问题：范围、用户、约束、成功长什么样。不要接受"优化仪表盘"作为结果，要逼到可观察的变化。
3. **按 `references/intent-template.md` 的模板写成 `intent.md`**，覆盖问题、期望结果、受影响的用户与系统、约束、待决问题。
4. **让提出者修正。** 意义归他，文字归 agent。提出者没读过的 `intent.md` 不许出门。
5. **提交到共享位置**，作者与时间戳随之进入记录。产品负责人从这里接手。

另外两条入口走同样五步：
- **工单已开** —— 读工单，起草 `intent.md`，转给产品负责人。
- **告警触发** —— 这是 `ai-sdlc-maintain` 把环闭回来的路径，agent 的诊断本来就按第 1 阶段的格式写。

## 关卡

| | |
|---|---|
| **人类负责人** | 产品负责人 |
| **决策** | 接受到设计阶段，或关闭 |
| **记录方式** | 制品的合并，或评审的关闭 |
| **"接受"触发什么** | 第 2 阶段（Design）——需求与设计一次性走完 |

产品负责人是**审阅并修正**，不是从零动笔。速度的全部收益就在这里：制品在会议本来该被排期之前就已经存在。

## 不要做

- 不要加故事点、估算或交付日期。它们在这套 playbook 里不属于任何阶段，只会把 Plan 消除掉的仪式重新引进来。
- 不要让 agent 编造提出者从未说过的约束。约束是事实，不是建议。
- 不要为了让制品看起来完整而删掉待决问题。被顺延的待决问题正是第 2 阶段必须回答或上报的东西。

## 怎么衡量

**领先指标** —— 从第一次对话到 `intent.md` 提交所花的时间，从提交的作者与时间戳读出。预期是数周的采集与细化周期缩短到数小时。

**滞后指标** —— 存活率：`intent.md` 中被接受进入设计阶段、而非被关闭的比例。另外统计首次 `spec.md` 提交**之后**仍在改 `intent.md` 的次数——每一次都代表一条需求漏了出去。
