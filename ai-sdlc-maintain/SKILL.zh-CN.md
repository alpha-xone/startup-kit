# AI 原生 SDLC · 第 6 阶段：Maintain（维护）

## 边界

只做一件事：**触发器在无人启动的路径上唤起 agent，它发现的东西以 `intent.md` 重新进入流水线。**

Maintain 不做超出有界 PR 的修复。能装进一个 PR 的发现走评审闸门；更大的一律变成 `intent.md`，从 Plan 开始。这就是让环成为环、而不是"一条告警后面站着一个人"的原因。

## 这个 skill 固化的转变

| | 传统 | AI 原生 |
|---|---|---|
| 性质 | 被动。凌晨三点的告警可能被漏掉 | 触发器在无人介入的路径上唤起 agent |
| 跟进 | 事故复盘的行动可能永远到不了代码库 | 发现以 `intent.md` 重新进入流水线，流向 Plan |
| 检测 | 常靠人工，或一个没人信的阈值 | **确定性**、纳入版本控制、单测覆盖，不涉及模型 |
| 判断 | 一切都由人决定 | 分级：1σ 记录，2σ 诊断，3σ 提议 |

承重的分离：**检测是确定性的；只有在控制带被突破之后才唤起模型。** 让模型决定何时醒来，等于用一个不可预测的系统去监控生产系统。

## 前置条件

环要重新进入的一切：

- `intent.md` 格式（`ai-sdlc-plan`）——环的结构化输出。
- 评审闸门（`ai-sdlc-deploy`）——发现像任何其他改动一样走它。
- 排练过的回滚路径（`ai-sdlc-deploy`）——最高自主权层级会调用它。

## 玩法：把环闭上

1. **挑一个有稳定滚动基线的指标。** 一个。候选：CI 测试失败率、部署后 5xx 率、PR 周期时长。
2. **写检测脚本。** 滚动窗口上的均值与标准差，配规则（Western Electric 或类似），让控制带既能抓尖峰也能抓缓慢漂移。脚本**纳入版本控制并有单测**，检测**不涉及模型**。这一步做错，下游全是噪声。
3. **在版本控制的配置里定义响应层级**（`bands.yaml`，模板见 `references/bands-yaml.md`）：
   - **1σ** —— 只记录。
   - **2σ** —— 只读方式唤起 agent 做诊断。
   - **3σ** —— agent 可以行动，但只能开 PR 进评审闸门，或触发**事先批准**的 runbook。
4. **选定触发层** —— 定时工作流、来自既有监控栈的 webhook，或内网 cron。agent 运行是无状态、非交互的，这才让一个环能无人启动地开始并结束。在 DSH 里，真正无人值守的触发需要挂载 `dsh-webhook-github`（默认未挂载）或外部调度器；`schedule_create` 是会话内提醒，**不是**生产调度器——别当调度器用。
5. **让 agent 把诊断写成 `intent.md`**，用第 1 阶段的格式：异常与证据、期望结果、受影响的系统、待决问题。此后这个发现就像其他东西一样走流水线。
6. **研判队列。** 服务负责人或值班工程师把面向产品的发现转给产品负责人。现在修、排期、或驳回。
7. **修复上线后补一个 eval**（`ai-sdlc-test`），让这一类问题被保护起来。

驳回路径很重要：**驳回用来调校控制带**并降低噪声。一个不把驳回反馈进阈值的流程，保证同一个误报永远复现。

## 层级纪律

| 层级 | 动作 | 为什么 |
|---|---|---|
| 1σ | 记录 | 便宜、不耗模型，并积累你调阈值时需要的记录 |
| 2σ | 诊断，只读工具 | 一个假设不花钱，还能告诉人该往哪看 |
| 3σ | 只提议：PR 或事先批准的 runbook | agent 的权限由别人事先批准的路径界定 |

值得照抄的替代项：
- CI 测试失败率突破 3σ → agent 隔离不稳定测试或开一个 revert PR；由评审闸门决定。
- 部署后 5xx 突破 3σ 且窗口内有部署 → agent 触发既有的回滚流水线。
- PR 周期时长触发漂移规则 → agent 给工程负责人写一份报告。同一套装置对流程指标和产线指标一样管用。

## 玩法：周期性代码扫描

一次安全扫描是关于某个代码库、在某个特定模型下的一份时点陈述，**两半都会过期**：代码每周在变，而每一代模型都会发现上一代漏掉的漏洞。

1. 接入仓库并按仓库、服务或团队组织，让发现的归属从一开始就清楚。
2. **第一次全量扫描作为基线**——包括以前被其他工具或更早模型扫过的仓库。预期它会在被认为干净的代码里找出问题。
3. 按项目设时间表。活跃开发的服务每周一次是合理默认；仓库大或混杂时限定到目录或分支。
4. **带着置信度评级研判。** 驳回时写原因，让驳回被记录、同一个发现下次不会当新的再来。
5. 有界的发现变成一个补丁，走 PR 评审闸门。提出修复的 agent 没有路径去批准它。
6. **比一个补丁更大的东西**——架构弱点、跨服务重复的模式——写成 `intent.md`，从 Plan 开始。
7. 修复进生产后，为那个漏洞类别补一个 eval。
8. 把发现导出到既有跟踪与审计系统，那是审计方本来就预期的地方。

覆盖度从上次运行起算，不是从第一次起算。模型驱动的扫描**补充**静态分析与依赖扫描；确定性的检查仍留在 CI。

## 玩法：频道里的 on-call

事故也会以聊天频道里晚上十点的一条消息到达。让 agent 以自己的身份成为该频道成员，每起事故就有了第一响应者，而响应过程本身成为环的一部分、也成为未来事故的记忆。

- **对话与组织知识留在频道里**；频道里任何人都能引导响应。
- 通过 MCP，agent 确认指标已回到基线并在串里确认。
- 它把复盘写进一份纳入版本控制的经验文件，供未来的调查读取。
- 小而边界清晰的修复以 PR 形式走评审闸门；更大的变成 `intent.md`。

频道就是审计链：请求、诊断、人工授权、修复，全都留在事故被处理的地方。

DSH 里没有聊天频道 agent。最接近的替代是人开着会话、带事故上下文进来，或挂载一个 webhook 触发器。说清楚你到底在做哪一种。

## 不要做

- 不要让模型决定何时醒来。检测保持确定性。
- 不要给 3σ 层级无限权限。它只能通过事先批准的路径提议，仅此而已。
- 不要驳回发现却不把驳回反馈进阈值。
- 不要把 `schedule_create` 说成生产调度器。它是会话内的，且只在会话活着时投递。

## 怎么衡量

**领先指标** —— 从控制带被突破到 `intent.md` 进入研判队列的耗时（检测器日志里两个时间戳都有）；已接入定时扫描的仓库占比；从发现到补丁进入评审的耗时。

**滞后指标** —— 变成已合并修复的发现占比；**同类事故的重复率**（应当随着修复不断给 eval 套件补用例而下降）；经过多轮扫描的仓库每次扫描的发现数；定时扫描发现的漏洞与生产中发现的对比较。
