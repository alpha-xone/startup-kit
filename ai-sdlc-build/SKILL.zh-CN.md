# AI 原生 SDLC · 第 3 阶段：Build（构建）

## 边界

只做一件事：**先产出并提交 `plan.md`，再实现它——组织知识编码成 agent 会读的文件，护栏以策略而非习惯的形式执行。**

Build 不决定做什么（那是 `ai-sdlc-design`），也不认证结果（那是 `ai-sdlc-test`）。

## 这个 skill 固化的转变

| | 传统 | AI 原生 |
|---|---|---|
| 起点 | 工程师读设计然后开始写码 | `plan.md` 先提交，计划模式本身在把关 |
| 方案在哪 | 工程师脑子里，或一条没人能审的评论 | 一份已提交的制品，后续阶段拿 diff 对照它 |
| 知识 | 在人脑和 wiki 里 | `AGENTS.md`/`CLAUDE.md` 与 skill，agent 会话开始时读取 |
| 护栏 | 习惯与评审者的警觉 | 钩子（确定性）与沙箱策略，垫在建议性的 skill 后面 |
| 并发 | 一次一个任务 | 多条工作流，工程师负责驾驶与评审 |

这个阶段价值最高的一条规则：**方案要在"改变方向仍然只是改一份文档"的时候被审。**

## 前置条件

- 期望有一份实现方案：已接受的 `spec.md`（小改动用 `intent.md`）。
- 一个 agent 能读的代码仓。
- 有帮助：仓库根目录已有 `AGENTS.md`（或现成的 `CLAUDE.md`）。

## 玩法：计划模式作为默认起点

1. **在计划模式里开会话** —— DSH 里用 `/plan`。计划模式是引导加一次受审的退出，不是能力锁；如果你要只读这个性质真的被强制，把沙箱同时设为 `read-only`。见 `references/harness-map.md`。
2. **把 `intent.md` 与 `spec.md` 交给 agent**，要求一份实现方案，点明会改哪些文件、工作顺序、以及证明它成立的测试。
3. **盘问方案。** 问：这可能弄坏什么？哪一步风险最高？你放弃了哪些选项，为什么？
4. **反复迭代，直到方案能独立成立** —— 检验标准：一个没看过这场对话的工程师，只凭 `plan.md` 就能实现这次改动。
5. **把批准的方案提交为 `plan.md`。** 模板见 `references/plan-template.md`。它进入审计链，PR 评审会拿最终 diff 对照它。
6. **接受方案并实现。** 方案扎实时，实现往往一遍过。
7. **实现偏离方案时，在同一个提交里更新 `plan.md`。** 一份悄悄和 diff 分叉的方案，比没有方案更糟。

关卡在任何代码存在之前：评审发生在改动还只是一份文档的时候。

## 玩法：自主实现

当护栏成熟之后——调好的 `AGENTS.md`、编码了政策的 skill、能拦住危险动作的钩子或沙箱策略、以及 agent 能自己跑的测试套件——自主执行会成为常规工作的默认：spec 紧凑、影响面小、测试已覆盖的代码。其余的路由到人工评审。

在 DSH 里这个旋钮是权限预设（`read-only` / `workspace-write` / `danger-full-access`），按会话选择。要注意它不是什么：DSH 没有"逐次编辑自动接受"的开关，所以这里的"自主模式"指的是会话的沙箱与审批策略，而不是绕过逐文件确认。

## 玩法：把组织知识做成文件

**`AGENTS.md`** —— 一个新同事第一天需要的上下文：约定、命令、架构，以及 agent 反复犯的错。

1. 让 agent 读完仓库先起草一份 `AGENTS.md`。
2. 砍到只剩新同事第一天需要的：构建/测试/lint 命令、真正重要的约定、agent 一直搞错的事。
3. 提交到仓库根目录，全团队共用一份。
4. 工作规则：**agent 同一个错犯第二次，纠正就写进 `AGENTS.md`。**
5. 控制在一页左右——它每个会话开头都被读，任何过期内容都是纯成本。

**skill** —— 给那些必须"被一致地应用"、而不只是"被知道"的知识。判断标准：

| 放进 | 当 |
|---|---|
| skill | 必须被一致应用、且有具名政策负责人的组织知识 |
| `AGENTS.md` | 每个会话都需要的仓库上下文：约定、命令、架构、反复出现的错误 |
| 提示词 | 只服务这一次任务的指令 |

1. 挑一件今天执行得不一致的事：一条安全标准、一个 API 约定、一条品牌规则。
2. 写成一个含 `SKILL.md` 的文件夹：frontmatter 说明*何时触发*，正文说明*做什么*。依据政策负责人的权威来源来写。
3. 放进仓库让它随代码走，或放用户级全局分发。（放法见 `ai-sdlc-design/references/harness-map.md`。）
4. **测试它会不会触发。** 用几种不同说法提同一个任务，确认每次都能加载。
5. 政策变更时，改 skill 并让政策负责人签字。

## 玩法：把确定性护栏垫在建议性 skill 后面

skill 是**建议性**的：它让 agent 倾向于遵守，但没有任何东西强制一个会话服从。必须永远成立的政策，需要在它后面垫一层确定性的东西。

- **确定性本地闸门** —— DSH 里就是沙箱与审批策略。给评审会话选 `read-only`，给无人看管的活儿选 `workspace-write` 而不是 `danger-full-access`，这就是可强制的那一层。
- **Claude Code 风格的钩子** —— DSH 自带桥接包（`dsh-hooks-claude-code`），能在 agent 运行期间执行现有的 `hooks.json`，支持 `PreToolUse`（拦截 / 转人工审批）、`PostToolUse`、`SessionStart`、`UserPromptSubmit`、`Stop` 以及子 agent 事件。它**已安装但未挂载**在 `web` profile 里；挂载方法与诚实的限制见 `references/harness-map.md`。

构建期有用的钩子：拦住对受保护路径的编辑（生成代码、冻结包）、编辑后跑格式化和 lint、别让凭据进 diff。构建期钩子要快且只针对被改的文件；重的检查放在提交或 PR。

**要人审批**的钩子属于发布闸门（`ai-sdlc-deploy`），不属于这里——构建途中的审批提示会把一个人重新放回所有并行会话的关键路径上。

## 玩法：并行工作与子 agent

两个常被混淆的机制：

| | 是什么 | DSH 机制 |
|---|---|---|
| **并行工作流** | 互不相撞的独立任务 | 分开的会话/工作区。按文件切分，用 `plan.md` 看清哪里是独立的。共享文件的任务放同一个会话里顺序做。 |
| **子 agent** | 单个会话**内部**的受限助手，有自己的上下文与工具上限，适合跨任务重复出现的工作 | `subagent`（全新上下文）与 `subagent_fork`（继承本对话）。默认后台；`send_message` 可转向；`list_agents` 可召回。 |

要紧的规则：
- 两三条并发流是合理的起点。上限是**一个人能认真评审多少条流**。
- 把重复出现的工作变成可复用的子 agent 提示：一个跑应用并报告的验证者、一个去掉多余复杂度的简化者、一个探索代码库但不用淹掉主上下文的研究者。
- 子 agent 的定义是一份仓库里的文件（名字、何时使用、可以碰什么），这样全团队共用。在 DSH 里这份文件是一个 skill 或一份有文档的提示模板——见 `references/harness-map.md`。

对于分散在很多独立片段上的工作，DSH 的 `workflow` 工具能跑一段脚本一次性编排大量子 agent。

## 不要做

- 不要在没有已接受 `plan.md` 的情况下动手实现。关卡就是这个阶段。
- 不要让 diff 与方案分叉却不更新方案。
- 不要把 skill 当成被强制执行的管控。说清楚哪一层真的在拦。
- 不要开超出评审吸收能力的并行流。没人审的吞吐量不是吞吐量。

## 怎么衡量

**领先指标** —— 一遍实现就合并的改动占比，以及从方案批准到 PR 合并的耗时（都取自 PR 元数据）。

**滞后指标** —— 每次改动的返工轮数，以及合并后的 diff 仍然与已提交 `plan.md` 相符的比例。
